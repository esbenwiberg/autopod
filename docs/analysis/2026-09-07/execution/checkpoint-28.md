# Checkpoint 28: retain branch work on failed approval push

Three initial RED manager regressions demonstrated that approval's no-new-changes path swallowed remote push failures and completed, and that a successful push settling after a generation replacement could complete the replacement lifecycle. The path now requires an actual successful push when accumulated branch work exists or branch emptiness is unknown. Failure or a missing branch identity raises BRANCH_PRESERVATION_FAILED (HTTP 502), persists an actionable reason, retains validated state and source resources, and does not emit completion. A new manager can explicitly retry from the persisted worktree and complete without starting a worker or creating a PR. A successful retry clears only this preservation-failure reason. Truly empty branches retain their existing no-push behavior.

Generation, status, branch/base, resource identity, execution mode and unanswered-decision checks surround the asynchronous work in this approval path. Stale diff/push/cleanup preparation stops with STALE_APPROVAL; a decision arriving during push remains actionable. The container-release guard also applies to deferred advisory cleanup. No stale operation can overwrite a replacement lifecycle in the covered fault-injection cases. This is not a claim of complete durable side-effect idempotency across all approval paths or processes.
