# Checkpoint 45: planned delivery, legacy recovery and operator visibility

The existing immediate transaction validates its confirmed publication, lifecycle, resource, decision and target identity; the later provider preparation boundary creates the actual admitted attempt. Repeated planning reuses the intent. Both existing PR and create-then-review paths survive restart and make their first merge request using the recorded source SHA, target and method. Planned and admitted states also survive an actual file-backed SQLite close/reopen. No new PodStatus or migration was introduced.

All merge polling now requires a durable delivery binding. The old unbound merge and rebase/force-push fallback is removed. Legacy pending rows without history become failed with original resources retained and an explicit Resume instruction; no provider status, merge, rebase, publication or container cleanup is required to reach that actionable state. The existing Resume path revalidates retained source without restarting the agent. The integration test then exercises the real readiness gate: a risky result requires an explicit fixture operator reason before approval. It does not weaken the gate or automatically approve the recovered source.
