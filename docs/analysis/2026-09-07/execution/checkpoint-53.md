# Checkpoint 53: commit polling owns its asynchronous observations

Three RED cases showed that clearing the polling timer did not revoke callbacks already awaiting Git. A late HEAD overwrote a replacement or stopped run's starting SHA and triggered another count query. A late count/timestamp overwrote the replacement's newer observations.

Commit polling now uses the existing serial polling coordinator. Each registration captures its lifecycle, exact container, execution target and source location. It checks registration and lifecycle ownership after each asynchronous command and before publishing metadata or checkpoint-status activity. Stopped or replaced callbacks cannot publish or start the next phase. A replacement registration waits for an earlier in-flight operation to drain, and missed ticks do not accumulate a command backlog. A fresh starting SHA discovered while the old command was pending is retained; counts computed against a superseded exclusion SHA are discarded.

The initial corrected cases passed three tests. Expanded actual pod lifecycle and polling suites passed 574 tests, including a command held across three polling intervals with one request in flight. The fixture generators now yield a final status event so the lint check accepts their intended asynchronous lifetimes. The daemon build and configured DTS passed. The original checkout still has only its pre-existing staged README and untracked analysis, image and strict-fetch specification paths. HEAD and worktree remained unchanged; exact passing identity and output are retained.

No new schema, profile/state field or operator control was introduced. This is local command-ordering evidence; it does not cancel a dispatched Git/checkpoint operation, prove durable cross-process ownership, or change the legacy handling of unavailable Git count output.
