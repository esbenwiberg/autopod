# Checkpoint 78: provider account reconciliation across startup cooldown

Two RED actual-manager cases reproduced a second container allocation after the originally authorized account was removed or changed provider identity during the sandbox startup cooldown. A control case editing the profile to another account while retaining the original account already behaved correctly. Startup resolved its bound profile before waiting and reused it after the cooldown without rechecking the account.

The existing startup ownership fence now also calls the existing effective-bound-profile resolver. This checks the original authorized account at each cooldown wake and again before starting the durable admission. Removed or incompatible accounts produce the existing actionable provider-binding error before another allocation. The consumed unstarted admission is cancelled with no fabricated execution duration. Editing the profile to another account still preserves the original account: neither credential lookup nor fallback touches the replacement account. Pending human decisions and replaced lifecycle handling from checkpoint 77 remain intact. This change neither rebases the configuration nor changes a model, account or retry allowance.

Ten focused cooldown and ownership cases passed, followed by 618 tests in four affected manager, retry-ledger, provider-attempt and deadline suites. These use real SQLite and mocked infrastructure, with a deterministic clock to inject the account change. No cloud or provider was contacted. Existing failure and retry operator contracts are unchanged; no additional native/browser interaction is claimed. The required full pipeline follows the scoped source commit with VITEST_MAX_WORKERS=4 recorded.

All six workstreams remain partial. This receipt covers account availability at the cooldown boundary, not every later asynchronous provisioning boundary or complete startup configuration identity.
