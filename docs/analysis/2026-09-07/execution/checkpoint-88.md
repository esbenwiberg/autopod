# Checkpoint 88: stop Delete after unverified cleanup

Three RED actual manager regressions showed container-removal failure, timeout and lifecycle replacement each allowing Delete to finish and continue source cleanup. The new deletion-cleanup module bounds the sequence to 25 seconds, checks ownership and deadline before and after each step, clears its timer, and rejects unverified cleanup with a readable 409. Late resolution cannot admit the next cleanup step. Container removal now precedes test-branch/worktree deletion. Delete checks status before stopping previews. Sidecar and network errors propagate in this strict path. Recorded sidecars without a manager, or test branches without configured cleanup capability/worktree, retain their records and reject deletion. Test-branch and sidecar helpers check ownership again before clearing metadata.

Seven targeted cases passed, including a task admitted during a pending cleanup, observed successful cleanup/timer disposal, retained test-branch metadata and a real Fastify rejection for unavailable sidecar cleanup. Four affected suites passed 759 tests. The native ActionHandler test passed five cases with a URLSession fixture; the new cleanup rejection retains the displayed pod and exposes the readable reconciliation reason. This is interaction-logic evidence, not visible native UI acceptance. No mobile/CLI Delete action surface was changed. Backend transport bodies are not exposed in the public cleanup error. A final ownership mismatch also returns the same 409 category before row deletion.

A deadline cannot undo an already admitted backend call, and this change does not provide durable exclusive cleanup ownership across controllers, restart or a second Delete. It detects supersession before subsequent work. Durable cleanup/reconciliation claims, historical accounting after deletion, and root/child lineage deletion remain unfinished. Existing optional network teardown capability remains as implemented; missing historical resource identity is not proof of cleanup. No migration, provider/model change, paid call, deployment or live mutation. All six workstreams remain partial. Required clean full validation follows.
