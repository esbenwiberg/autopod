# Checkpoint 101: attached reply delivery and original responder preservation

Three actual MCP client/server plus processPod/sendMessage lifecycle reproductions dropped attached ask_human, report_blocker and request_credential responses after their waiters resolved. Each lost the pending guidance despite an otherwise healthy stream. Normal attached replies now enter the durable guidance queue in the decision transaction before the waiter resolves. Credential-result notification joins the same decision/state/queue transaction, keeping the human reply and its actor separately from the nonsecret authentication status sent to the worker. Acknowledgment uses checkpoint 100's generation/run-bound immutable receipt.

Successful MCP results append a receipt marked with the completed tool, instructing the worker to acknowledge the saved messages without repeating an already completed action or treating the receipt as new approval. Dropped results remain replayable through check_messages. This does not change budget approval, host credential repair, provider identity or action authorization semantics. Credential injection remains an external operation before this transaction; this checkpoint proves atomic notification/decision recording, not exactly-once credential installation.

The attached ask_human continuation also overwrote responder metadata after the manager had recorded the human's answer. Replaying the original writer against the new lifecycle test independently reproduced the missing actor. The bridge now checks/resolves under the repository transaction: an identical response preserves the original metadata; a conflicting response fails. This is independent of acknowledgment.
