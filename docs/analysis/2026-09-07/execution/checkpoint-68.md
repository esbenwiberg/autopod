# Checkpoint 68: bounded selected reviewer acquisition

Two initial RED actual-engine regressions showed that pending provider-client/credential acquisition ignored the review timeout and that each API tier received a fresh full budget. The selected profile API route now uses a monotonic deadline spanning acquisition and request allocation. Acquisition races its remaining timeout and validates the deadline again after resolution. A late client cannot revive the expired caller or dispatch a provider request. Invalid or exhausted budgets refuse acquisition. The underlying credential operation may still settle or update its own cache; this is not cancellation proof.

Direct API dispatch recomputes remaining time after the trusted provenance callback, with SDK retries still disabled. Tool review acquires the selected client before allocating remaining time. Acquisition and earlier API tiers therefore consume the same configured review interval. Deadline failures mark required review unavailable, preserve earlier findings and measured usage, and forbid automatic replay, host fallback or a council replacing the missing required execution. No task-wide durable admission claim is made.

An additional RED test exposed acceptance processing of a late direct API response. The engine now retains its filtered findings and known tokens but rejects its verdict at the deadline, including standard-depth review. An SDK transport that ignores timeout and never settles remains outstanding; no remote cancellation or bounded remote execution is inferred from these local checks.

The first broader run failed only the former exact 300000ms SDK-timeout assertion, which now checks a positive bounded remaining value. The final three affected suites passed 775 tests. All seven build/configured DTS tasks passed.
