# Checkpoint 89: WAL-safe destructive-migration backups

Two RED reproductions showed that the cutover hook copied stale main-file bytes while committed data remained in WAL, and accepted an unrelated dbPath as the backup source. Destructive migrations now use the awaited runMigrationsWithBackups path at daemon startup. It inspects and freezes SQL before execution, uses the open database's online backup API, validates source-path identity, verifies integrity and foreign keys, records all-table watermarks/checksum, and publishes private files plus a standard version-2 restore receipt without replacing or pruning prior backups. It checks headroom for two logical database copies plus 128 MiB before backup. A private staging directory protects in-progress files; snapshot and receipt files plus the destination directory are fsynced before success.

The synchronous runner supports in-memory, empty and non-cutover upgrades; populated destructive upgrades must use the awaited runner. Database data/schema changes, same-connection writes, migration SQL changes, or a source-path replacement during backup prevent migration. Backups made before such changes remain point-in-time evidence, not permission to apply a stale migration. The online API preserves implicit row IDs; VACUUM was not substituted because SQLite documents that it can change them: https://www.sqlite.org/lang_vacuum.html . The backup API's behavior is documented at https://www.sqlite.org/backup.html .
