# Checkpoint 24: task-wide sandbox startup admission

A desired-behavior manager regression reproduced the exhausted sandbox retry allowance resetting on Resume after two failed starts. The initial test fixture lacked a retained worktree and exercised the existing no-worktree rejection; the corrected RED fixture supplies a preserved worktree and observes Resume incorrectly returning retry-agent. The final integration uses actual SQLite repositories, a recreated manager, mocked sandbox failures, and authenticated Fastify routes. It proves blocked Resume leaves the pod and source identity unchanged, a linked fix cannot allocate another sandbox, an idempotent human grant authorizes one separate attempt, and its failure does not replenish the automatic allowance.

The existing task retry tables already have a stage dimension, so no migration is needed. The shared ledger now supports separate validation and sandbox_startup stages, including scoped policy, attempts, authorization, execution, settlement and interrupted recovery. Read-only eligibility checks share the same evaluator as transactional admission. Stage mismatches cannot reuse a request key or start/settle another stage's attempt. Policy and one-use decisions remain immutable, and lifecycle/decision/binding guards remain enforced.

Sandbox startup is admitted after fresh source preparation and before provisioning, sidecars or sandbox allocation. Its default policy allows one delayed retry after a safe typed startup transport failure. The persisted backoff is checked again when execution starts. Startup settles on the first runtime event, successful interactive setup, or successful preparation for validation/completion-only recovery; those receipts do not claim the agent, validation or delivery succeeded. Unfinished admissions recover as unknown with no fabricated duration. A real manager cooldown fault test proves a superseding generation cannot allocate the second sandbox; the consumed admission and unknown outcome survive. Measured startup duration is separate from token or infrastructure price accounting.

The task policy cannot be widened by Resume, a fresh manager or a linked pod. On first policy creation, known legacy infrastructure-recovery counters across the task reduce the automatic allowance. Existing Resume/rework no longer zero those counters. Historical counters are lower bounds; this does not reconstruct missing historical attempts, conditions or costs. Legacy manual Resume without a prior stage receipt retains its existing behavior, while the known automatic allowance is reduced. Complete historical reconciliation remains open.

Startup does not yet have a verified running environment when admission occurs. Its relevant input hashes are explicitly unavailable rather than derived from requested image/resource settings. Unknown or nonretryable startup retries therefore require a recorded override; a changed requested image is not falsely treated as verified repair. Runtime/model/provider/account identity remains pinned independently. Broader provider recovery after the first runtime event, repository rework admission and complete phase cost accounting remain unfinished.

The existing retry API accepts an explicit validated stage; validation remains the default. CLI retry-state and authorize-retry support --stage sandbox_startup. Mobile shows a separate startup panel for sandbox pods, and desktop loads a separate card when recorded attempts exist. Stage-specific authorization drafts survive a lost response/reload without crossing stages. The native retry card now propagates Resume failures instead of showing an accepted request after a swallowed error.
