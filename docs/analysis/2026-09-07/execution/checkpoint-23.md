# Checkpoint 23: coordinate interactive completion and retain current authority

Five actual-manager RED cases reproduced duplicate branch/artifact operations, conflicting promotion while a completion was pending, bypassed pending input, and an old push completing a replacement running lifecycle. Completion now uses a small dedicated coordinator keyed by pod, lifecycle generation and a hash of the requested options. Identical concurrent requests share one pending operation. Conflicting requests return COMPLETION_IN_PROGRESS; settled failures release coordination so an explicit retry can proceed. Request contents are not logged or retained as a plaintext coordination key.

Interactive completion checks current generation, running/interactive mode, output, branch/base, execution target, worktree, container and durable unanswered decisions before work and after asynchronous source/push boundaries. The repository's decision check includes unresolved older cycles hidden by legacy pointer drift. A stale continuation returns STALE_WORKSPACE_COMPLETION; an outstanding question returns HUMAN_DECISION_PENDING when otherwise current. These errors cannot be swallowed by the best-effort push catch and followed by cleanup.

Container cleanup accepts a caller-supplied release guard for this path. It rechecks before release, after preview/pre-cleanup waits, and after the container operation before shared bookkeeping. A question arriving during pre-cleanup work preserves the container. A replacement generation installed while old cleanup returns cannot be completed or have its identifiers cleared. Post-completion event/linked-follow-up publication also stops when its generation was superseded during later asynchronous work. An already-dispatched external operation cannot be undone by these checks; broader durable phase/side-effect ownership remains unfinished.
